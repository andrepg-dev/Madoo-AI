# 103 — Fix: hero/found images render in editor but not in screenshot/inbox (AVIF)

## Symptom
A generated email's hero **background image** showed in the in-app editor
preview but came out **blank/black** in the library preview card (and would also
break in real inboxes). Happened "desde hace tiempo" on certain images.

## Root cause (traced end-to-end)
The failing asset (`.../found-images/038380f7-…-027fe223a5eb.jpg`) is served
with `Content-Type: image/avif` — it is **AVIF data with a `.jpg` key**.

Chain:
1. `rehostImageUrl` (`generation.service.ts`) downloads web images for find_images
   with `Accept: image/avif,image/webp,…`, so the source CDN content-negotiates
   to **AVIF**, and the bytes are re-hosted to S3 with `image/avif`
   (`s3.uploadBuffer`; the `.jpg` extension is just the `extByType` fallback).
2. The library card is a **server screenshot** (`<img src={previewUrl}>` in
   `template-card.tsx`), generated by Puppeteer.
3. **Prod runs Alpine `chromium`** (`Dockerfile`: `apk add chromium`,
   `/usr/bin/chromium-browser`), which does **not decode AVIF**. The editor
   preview is an iframe in the user's desktop Chrome, which **does** → the
   image shows there but is blank in the screenshot.
4. AVIF is also unsupported by most email clients (Gmail/Outlook), so it would
   break in inboxes too.

Confirmed: `curl` → `content-type: image/avif`; local Chrome-for-Testing decodes
AVIF (so local looked fine); prod Chromium is Alpine; `sharp` decodes the file
as `heif 1880x1058`.

It was NOT a screenshot timing/`background-image`-await issue, NOT a variable
substitution issue (editor + screenshot use the same `compiledHtml`), and NOT a
URL-access issue (S3 returns 200).

## Fix
Transcode any non-email-safe image to JPEG (PNG when it has alpha) **at the
single hosting choke point**, so every ingress path is covered (found-images,
user email-image uploads, avatars). Screenshots (PNG) and JPEG/GIF pass through.

- `apps/backend/src/common/image-transcode.ts` (new): `isEmailSafeImageType`,
  `toEmailSafeImage` (sharp). Safe set = jpeg/png/gif.
- `apps/backend/src/s3/s3.service.ts`: `uploadBuffer` now normalizes via
  `toEmailSafeImage` (falls back to original bytes if transcode throws); added
  `image/avif` to the extension map; new `listKeys` / `getObject` /
  `putObjectAtKey` helpers for the backfill.
- Added dependency `sharp@^0.35.2` (lockfile carries linuxmusl + libvips musl
  prebuilts → installs in the Alpine image).

## Existing images (backfill)
`apps/backend/src/scripts/backfill-image-formats.ts` (new) +
`pnpm backfill:image-formats` script. Rewrites email-unsafe S3 objects **in
place (same key)** so URLs already baked into existing emails keep working — no
DB rewrite. Supports `--prefix` (default `found-images/`), `--limit`,
`--dry-run`.

## Deploy / run steps (prod is manual)
1. Rebuild backend image so `sharp` is installed:
   `cd /root/Madoo-AI/apps/backend && git pull && docker compose up --build -d`.
   Verify sharp loads: `docker exec madoo-backend node -e "require('sharp');console.log('sharp ok')"`.
2. Backfill existing AVIF/WEBP assets (dry-run first):
   `docker exec madoo-backend pnpm backfill:image-formats -- --dry-run`
   then without `--dry-run`. Repeat for `--prefix email-images/` and
   `--prefix avatars/` if desired.
3. Existing emails referencing the rewritten keys fix immediately. Their cached
   `previewUrl` screenshots may need regeneration (`backfill-email-previews`)
   only if you want the thumbnails refreshed.
